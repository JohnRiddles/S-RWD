# README

This repository contains code used for the S-RWD: Synthetic Data for Real-World Data Project. This is an NSDS (National Secure Data Service) Demonstration project implemented throug the America's Datahub Consortium. It involves generating synthetic health data using the CEHR-GPT package. Included code shows applications of this approach to Synthea within the Oak Ridge National Laboritory's Frontier supercomputer, as was as N3C (National Clinical Cohort Collaborative) data within the National Center for Advancing Translational Sciences' N3C Data Enclave.

The repository is organized into four directories.

## Data Generation

This directory contains scripts that were used to generated synthetic data sets with two different source data sets and run in two different environments. One was used to generate data within the Oak Ridge National Laboratory's Frontier supercomputer using Synthea data. The other generates data based on N3C and is run within the N3C Enclave. These scripts can be adapted to work with other data sets and environments but are specifically designed for data in the OMOP format. Java (version 8 or 11) and Spark are a required dependencies. 

The model used was CEHR-GPT. https://github.com/knatarajan-lab/cehrgpt. A copy of the CEHR-GPT source code, as well as source code for two interdependent packages, CEHR-BERT and CEHRBERT-Data, must be kept on the system in which the generation scripts are ran. The CEHR-GPT package will not work with N3C out of the box, so the package source was patched at run-time in our code base, which requires having the source code directly available.

The original CEHR-GPT repository is available here: https://github.com/knatarajan-lab/cehrbert_data

CEHR-BERT: https://github.com/cumc-dbmi/cehrbert

CEHRBERT-data: https://github.com/knatarajan-lab/cehrbert_data

The model treats longitudinal patient histories as a "language" modelled by the GPT architecture. The model's use of Artifical Time Tokens (ATTs) allow for the modeling of irregularly spaced events. The model does treat input data as a linear sequence, which requires flattening hiearchical structures, though this is handled by the package.

The model pipelines contain a number of steps. 

1. A preprocessing step where the input OMOP tables are converted to patient sequences. Concepts that occur rarely in the input data are excluded. Otherwise, memory usage and run-time would reach infeasible limits. The specific limit is set by the 'min_num_of_patients' parameter.

2. The CEHR-GPT model is training on patient sequences.

3. Synthetic sequences are generated by the trained model.

4. Synthetic sequences are converted into OMOP tables.

5. Post-processing adjustments for synthetic OMOP data, particularly the assignment of random birth dates.

The Synthea/ORNL script (**Synthea_full_pipeline.ipynb**) is a relatively straightforward application of this pipeline. This is the script that would be used and adapted for most environments and data files. The N3C script, **N3C_full_pipeline.ipynb**, is much more involved, with additional steps for environment management for working with system resets and the Maestro package management system. It also includes hotfixes that patch the original CEHR-GPT back to allow it to work with N3C data.

## Risk Assessment

This directory contains code used to assess disclosure risk of the synthetic data sets based on both Synthea and N3C. Code for each of these are kept in separate directories. Synthea itself is public, so should not have high disclosure risk in the source data, let alone the synthetic data, but it was used to test functionality. 

Risk assessment measures included in this package belong to two broad categories:

- Identity disclosure (re-identification): Identification of an individual by an intruder by exploring indirect identifiers. The following metrics are included:
    - UiS (% Unique in Synthetic): The percentage of records in the synthetic data that are unique with respect to select quasi-identifiers.
    - UiO (% Unique in Original): The percentage of records in the source data that are unique with respect to select quasi-identifiers.
    - RepU (Replicated Uniques): Among unique source records, % also unique in the synthetic data.
    - UiOiS (% Unique in Original in Synthetic): The percentage of records that are unique in the source that also appear in the synthetic data.

- Attribute disclosure: Sensitive values that may be inferred are attribute disclosure risks. If may be possible, for example, to analyze synthetic data to infer that all elderly mean in a small geographic area have dementia. The following metrics are included. 
    - Dorig (% Disclosive in Original): The percentage of source records that are disclosive, i.e, target attributes can be predicted from other attributes.
    - Dsyn (%Disclosive in Synthetic): The percentage of synthetic records that are disclosive.
    - DiSCO (Disclosive in the Synthetic and Correct): The proportion of the source records where quasi-identifiers in the synthetic data lead to correct prediction of attributes in the source data.
    - DiSDiO (Disclosive in Synthetic Disclosive in Original): A version of DiSCO limited to cases that are disclosive in the source data.
    - TCAP (Targeted Correct Attribution Probability): The probability that an adversary with an correctly infer a sensitive attribute for an individual known to be in the source data.
    - TCAP_1 (Targeted Correct Attribution Probability - Target 1): TCAP limited to health condition targets, with binary outcome 0/1, where value = 1, and 1 is assumed to be the sensitive outcome.
    - TCAP_0 (Targeted Correct Attribution Probability - Target 1): TCAP limited to health condition targets, with binary outcome 0/1, where value = 0.

## Use Case Analysis

This directory contains code used to perform a use case analysis based on an N3C COPD cohort. This use case looks at influenza vaccine effectiveness using a test-negative design. This contains the following subdirectories

### Use Case Analysis Data Preparation

The subdirectory 'Use-Case-Analysis-Data-Preparation' is used to prepare data for the use-case analysis. The programs in that subdirectory are structured for use in the Palantir Foundry platform used for N3C. They are specifically structured as a [Python transform](https://www.palantir.com/docs/foundry/transforms-python/transforms), which is a set of Python programs that specify a sequence of transformation steps that take a collection of input files and produce a set of output files and intermediate files. The programs take as input a set of OMOP tables and some user-defined configuration files that identify concept sets or metadata used for defining transformations. There is a subdirectory named 'datasets' that defines transforms for the original data, and a subdirectory named 'synthetic_datasets' that defines transforms for the synthetic data.

### Concept Sets and Config Files

The subdirectory 'Concept-Sets-and-Config-Files' primarily contains CSV files which list or define concept sets used in the analysis. It also contains one small configuration file that is used in a data transformation step. The only concept sets that are explicitly defined in these files (i.e., by listing specific concept IDs for a concept set) are those that are not already defined in the N3C table 'concept_set_members'.

### Use Case Data Analysis

The subdirectory 'Use-Case-Data-Analysis' contains R scripts used to complete final data preparation steps and conduct the use case analysis. It contains the following scripts:

- 'palantir-foundry-helper-functions.R': A set of R functions used to simplify data access, especially for large datasets stored as collections of Parquet files.

- 'prepare-use-case-analysis-data.R': A sequency of data subsetting and transformation steps that build upon the Python transform described earlier. The result is a dataset in Palantir Foundry that contains exactly the set of cases and variables needed for all analyses. It results in a dataset named 'use_case_analysis_data'.

- 'prepare-synthetic-use-case-analysis-data.R': A copy of the previous script, but adjusted to work for the synthetic datasets. It results in a dataset named 'synthetic_use_case_analysis_data'.

- 'conduct-use-case-analysis.R': This script conducts the use case analysis, separately for the original data and for the synthetic data. It then combines the analysis results from both datasets into combined summaries.

## Utility Assessment

This directory contains code used to assess data utility for the synthetic data sets based on both Synthea and N3C. This also includes a directory containing an R package, synthassess, which implements a variety of utility and other quality measures. The primary evaluations involve comparing distributions between the source and synthetic data sets. Specific comparisons include the following.

- Number of unique values for different variables each data set.
- Comparison of missingness rates
- Kolmogorov-Smirnov statistics for comparison of continuous values
- Hellinger distance for comparison of categorical values
- Average difference in correlation coefficients
- Average difference in Cramer's V
- Confidence interval overlaps
- U-Statistic (a global utility measure that measures multivariate associations)

The scripts for utility assessment require a configuration file that specifies whether a variable is categorical, continuous, or should not be evaluated.
Examples of such configuration files are included in both the Synthea and N3C directories.

The synthassess directory contains an R package with functions that can be applied in general situations.
